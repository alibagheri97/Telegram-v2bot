# ربات فروش VPN تلگرام

یک ربات فارسی مبتنی بر `pyTelegramBotAPI` (TeleBot) برای فروش و مدیریت اشتراک‌های پنل سازگار با V2Board/XBoard. دیتابیس ربات کاملاً از دیتابیس پنل جداست؛ ربات فقط جدول `v2_user` را از طریق یک کاربر محدود MariaDB می‌خواند/ویرایش می‌کند و هیچ migration روی پنل اجرا نمی‌کند.

## امکانات پیاده‌سازی‌شده

- سه سطح دسترسی: مدیر اصلی (`0`)، نماینده (`1`) و کاربر (`-1`)
- ثبت‌نام فارسی، کد دعوت، ساخت خودکار اکانت آزمایشی یک‌روزه و QR
- اشتراک نامحدود زمانی با ۱/۲ اتصال و اشتراک حجمی ۱۰ تا ۵۰ گیگ با گام ۵ گیگ
- پیش‌فاکتور، کارت‌به‌کارت، دریافت تصویر/فایل رسید، ارسال به گروه/تاپیک و تأیید یا رد اتمیک
- قفل مالی سفارش باز: تا تأیید، ارسال مجدد رسید ردشده یا لغو سفارش قبلی، خرید و پرداخت جدید بسته می‌ماند
- داشبورد کاربر، اشتراک‌ها، وضعیت رنگی، QR، کیف پول، دعوت دوستان، راهنما و پشتیبانی
- تمدید خودکار از کیف پول و اعلان پایان اشتراک آزمایشی
- داشبورد مدیر اصلی، فهرست صفحه‌بندی‌شده پنل و کاربران، sort/search امن و عملیات مدیریتی
- ساخت اکانت توسط نماینده، کسر از کیف پول و نمایش اکانت‌های ساخته‌شده
- قیمت‌ها و تنظیمات قابل‌ویرایش، گزارش فروش و دفتر تراکنش کیف پول
- stateهای گفتگو در دیتابیس (مقاوم در برابر restart) و تست واحد

## راه‌اندازی

### نصب v1 و به‌روزرسانی نسخه‌ها

پیش‌نیاز لینوکس: Python 3.11+ به همراه venv/pip، MariaDB، git و systemd. اجرای نصب با root یا کاربر معمولی دارای sudo پشتیبانی می‌شود. در نصب root، سرویس با یک حساب سیستم مستقل و بدون دسترسی root اجرا می‌شود:

```bash
./start.sh
```

نصب تعاملی نام برند و تنظیمات پایه را می‌گیرد، دیتابیس مستقل و کاربر محدود ایجاد می‌کند، کد یک‌بارمصرف `/auth` می‌دهد، و سرویس برند را نصب می‌کند. نسخه اجراشونده در `.runtime/releases/` جدا از پوشه توسعه آماده می‌شود. `.env`، rootها، موجودی‌ها، قیمت‌ها، فایل‌های نسخه‌های قبلی و دیتابیس در به‌روزرسانی بازنویسی نمی‌شوند. API برند به‌صورت پیش‌فرض فعال نمی‌شود؛ این مسیر به‌روزرسانی برای سرویس اصلی ربات است.

برای نصب قدیمیِ بدون launcher، فقط یک بار مهاجرت لازم است؛ این مرحله یک restart کنترل‌شده دارد:

```bash
./update.sh --adopt
```

پس از این مهاجرت، بروزرسانی عادی از `systemctl restart/stop` استفاده نمی‌کند. نسخه جدید و وابستگی‌هایش جداگانه آماده می‌شوند، config/DB/Telegram token بررسی می‌شود، و سپس SIGHUP باعث drain شدن درخواست‌ها و جابجایی همان PID به نسخه جدید می‌شود. systemd فعال می‌ماند و هم‌زمان دو poller اجرا نمی‌شوند. **به‌معنای صفرثانیه وقفه تلگرام نیست**: پایان long-poll یا یک عملیات طولانی ممکن است handover را عقب بیندازد. offset دریافت پیام به نسخه بعد منتقل می‌شود. در crash یا تغییر ناسازگار، دسترس‌پذیری بی‌وقفه قابل تضمین نیست.

روی ماشین توسعه، شماره نسخه را در `VERSION`، `pyproject.toml` و `vpnshopbot/__init__.py` به‌روز و تغییرات را تست کنید؛ سپس:

```bash
./make-release.sh
# فایل dist/vpn-shop-v1.0.0.tar.gz و checksum آن را به سرور منتقل کنید.
```

روی سرور، از پوشه اصلی پروژه:

```bash
./update.sh /path/to/vpn-shop-v1.0.0.tar.gz --sha256 SHA256_FROM_THE_RELEASE
# یا patch یکپارچه git، با شماره نسخه جدید:
./update.sh --patch /path/to/change.patch --version 1.1.0
# بازگشت کد به نسخه قبل، بدون بازگرداندن دیتابیس:
./update.sh --rollback
```

بسته‌ها فقط فایل‌های مجاز پروژه را می‌پذیرند؛ مسیر traversal، symlink، فایل config واقعی و checksum غلط رد می‌شود. بررسی اولیه قبل از handover انجام می‌شود؛ در شکست، اشاره‌گر نسخه قبلی بازیابی می‌شود و systemd طبق سیاست restart خودش تلاش می‌کند. اگر handler مالی گیر کرده باشد، updater آن را برای سرعت بیشتر kill نمی‌کند؛ وضعیت را با journalctl بررسی کنید. نسخه‌ها برای rollback نگه داشته می‌شوند؛ پاکسازی خودکار و مخرب نداریم.

فقط migration افزایشیِ سازگار با نسخه قبلی مجاز است؛ این updater فقط جدول غایب را ایجاد می‌کند و تغییر ستون یا migration مخرب انجام نمی‌دهد. rollback کد، داده‌های مالی یا schema دیتابیس را rollback نمی‌کند. قبل از انتشار تغییرات schema، برنامه migration و بکاپ مستقل داشته باشید. checksum سلامت انتقال را بررسی می‌کند، نه هویت ناشر؛ فقط بسته/patch مورداعتماد خودتان را اجرا کنید.

در GitHub خصوصی، push یک tag مانند `v1` پس از موفقیت تست‌ها، بسته و checksum را به Release همان مخزن منتشر می‌کند. توکن‌ها، رمزها، `.env` و cacheهای محلی در Git یا bundle قرار نمی‌گیرند.

### نصب خودکار پیشنهادی

برای هر clone جدید فقط اسکریپت تعاملی را اجرا کنید:

```bash
./start.sh
```

اسکریپت نام برند، توکن، مشخصات MariaDB و پنل، آدرس subscription، پلن آزمایشی، گروه و topic رسیدها، پشتیبانی، کارت و timezone را می‌پرسد. سپس:

1. یک دیتابیس مستقل و کاربر محدود MariaDB می‌سازد؛
2. فایل امن `.env` را با سطح دسترسی `600` ایجاد می‌کند؛
3. یک رمز یک‌بارمصرف شش‌رقمی با اعتبار ۳۰ دقیقه تولید می‌کند؛
4. سرویسی مثل `starlight_bot.service` را نصب، enable و start می‌کند؛
5. منتظر می‌ماند تا اولین مدیر در تلگرام دستور `/auth 123456` را ارسال کند.

اولین احراز هویت موفق، همان Telegram account را مدیر اصلی می‌کند. پس از آن `/auth` برای همیشه روی آن دیتابیس غیرفعال است. هر حساب حداکثر پنج تلاش و کل فرایند حداکثر سی تلاش ناموفق دارد. رمز خام در فایل ذخیره نمی‌شود و فقط hash آن در `.env` قرار می‌گیرد.

اگر فقط آماده‌سازی سرور را می‌خواهید و فعلاً نباید ربات اجرا شود:

```bash
bash install-prerequisites.sh
bash start.sh --prepare-only
# فقط وقتی برای ورود تنظیمات، ساخت دیتابیس و نصب سرویس آماده‌اید:
bash start.sh
```

اسکریپت پیش‌نیاز، Python/venv/pip/git را نصب می‌کند؛ MariaDB یا سرویس پنل را نصب مجدد یا restart نمی‌کند. در Ubuntu قدیمی، اگر Python 3.11 در مخازن همان سیستم موجود نباشد، پیام واضح می‌دهد و PPA ناشناس اضافه نمی‌کند. می‌توانید با `PYTHON_BIN=/path/to/python3.11` مفسر معتبر را مشخص کنید. venv خراب یا قدیمی به‌جای حذف، با نام `.venv.incompatible-...` نگه داشته می‌شود.

در نصب root، فایل `.env` فقط برای root و گروه حساب سرویس قابل خواندن است؛ وضعیت اجرایی داخل `.runtime/state/` نگهداری می‌شود. حساب ربات اجازه نوشتن در کد و مسیر اشاره‌گر نسخه‌ها را دریافت نمی‌کند. پروژه را ترجیحاً خارج از document root وب قرار دهید؛ اگر داخل `wwwroot` است، دسترسی HTTP به کل پوشه ربات را در تنظیمات وب‌سرور مسدود کنید.

### نصب دستی

پایتون ۳.۱۱ یا بالاتر لازم است:

```bash
python3 -m venv .venv
.venv/bin/pip install -e '.[dev]'
cp .env.example .env
# مقادیر .env را تکمیل کنید
.venv/bin/python -m vpnshopbot.app --init-db
.venv/bin/python -m vpnshopbot.app --check
.venv/bin/python -m vpnshopbot.app
```

توکن، رمزها و شماره کارت فقط در `.env` نگهداری می‌شوند و این فایل در Git ignore شده است. چون توکن فعلی در گفتگو افشا شده، پیش از استفاده عمومی آن را از BotFather باطل و جایگزین کنید.

## تنظیمات ضروری

- `ROOT_TELEGRAM_IDS`: شناسه عددی مدیران اصلی، جداشده با ویرگول
- `SUBSCRIPTION_BASE_URL`: آدرس HTTPS اشتراک تا قبل از مقدار token
- `PAYMENT_GROUP_ID`: شناسه منفی گروه رسیدها
- `PAYMENT_TOPIC_ID`: شناسه topic رسیدها؛ برای گروه بدون topic مقدار صفر
- `TRIAL_*`: پلن، گروه، مدت و حجم اشتراک آزمایشی پنل

ربات باید در گروه رسیدها admin باشد. برای گرفتن شناسه گروه و topic می‌توان موقتاً logging تلگرام را فعال کرد یا از یک ربات ID helper معتبر استفاده کرد.

روش پیشنهادی و امن‌تر برای اتصال topic رسیدها:

1. ربات را در گروه Forum به‌عنوان admin اضافه کنید.
2. مدیر اصلی ربات داخل همان topic رسیدها دستور `/set-topic recipt` یا `/set_topic recipt` را بفرستد.

ربات شناسه واقعی منفی گروه و `message_thread_id` را مستقیماً از پیام می‌گیرد؛ بنابراین نیازی به وارد کردن دستی IDها نیست. دستور فقط از Telegram account ثبت‌شده به‌عنوان root پذیرفته می‌شود و فرستنده دستور و خود ربات نیز باید در گروه admin باشند.

## دستورات مدیر اصلی

### سرویس انقضا

از داشبورد مدیر اصلی، «⚙️ مدیریت سرویس‌ها» را باز کنید. سرویس جدید انقضا ابتدا متوقف است؛ پس از تنظیم تاپیک و ثبت مالکیت اکانت‌های خودتان، آن را فعال کنید. گزینه «یک بار بررسی اکنون» حتی هنگام توقف سرویس، یک بررسی و ارسال واقعی انجام می‌دهد. زمان آخرین اجرا، نتیجه بررسی و فهرست Driving List اشتراک‌های پایان‌یافته در همین قسمت نمایش داده می‌شود. تمدید خودکار از کیف پول نیز جداگانه قابل توقف/فعال‌سازی است.

- داخل تاپیک Expired با حساب مدیر اصلی بفرستید: `/set-topic expired`. این تنظیم مستقل از تاپیک رسیدهاست و دسترسی مدیر گروه و ربات بررسی می‌شود.
- سرویس هر ۱۵ ثانیه، انقضای زمانی و تمام‌شدن حجم را بررسی می‌کند؛ زمان صفر یعنی بدون انقضا. اعلان هر دوره انقضا در دیتابیس ثبت می‌شود و پس از restart دوباره ارسال نمی‌شود. شکست ارسال یک حساب، مانع بررسی دیگر حساب‌ها نمی‌شود و در نوبت بعد دوباره تلاش می‌شود. برای رعایت محدودیت تلگرام، هر سرویس حداکثر دو اعلان گروهی در هر نوبت ارسال می‌کند؛ صف بزرگ ممکن است دیرتر تحویل شود.
- فقط اکانتی که سابقه سازنده روت دارد به تاپیک Expired ارسال می‌شود. ارتقای خریدار یا ادمین به روت، اکانت‌های قبلی او را «ساخته‌شده توسط روت» نمی‌کند. اکانت ناشناس پنل نیز خودکار به روت نسبت داده نمی‌شود.
- برای اکانتی که خودتان مستقیماً در پنل ساخته‌اید، در دیتابیس V2 جزئیاتش را باز کرده و «ثبت اکانت ساخته‌شده توسط من» را تأیید کنید. اکانت نباید از قبل به هیچ کاربر ربات یا ادمین دیگری متصل باشد. این کار تنها در دیتابیس ربات، مالکیت و سابقه سازنده را ثبت می‌کند؛ ساختار دیتابیس پنل تغییر نمی‌کند.
- اعلان گروهی شامل تمدید سریع **۳۱ روزه، صفرکردن مصرف و رفع مسدودی** و لینک خصوصی وضعیت اکانت است. فقط روت می‌تواند تمدید سریع را اجرا کند؛ عملیات روی پنل قفل و در یک تراکنش اجرا می‌شود و اعلان قدیمی/تکراری باعث تمدید دوباره نمی‌شود. این عملیات مدیریتی روت هزینه‌ای از کیف پول کسر نمی‌کند.
- ادمین برای مشتری‌های خودش اعلان خصوصی با تمدید طبق قیمت اختصاصی دریافت می‌کند؛ خریداران عادی اعلان خصوصی با مشاهده اشتراک و خرید دریافت می‌کنند. این اکانت‌ها وارد تاپیک Expired نمی‌شوند.
- ثبت موفق تحویل و ارسال تلگرام، یک تراکنش مشترک ندارند؛ در قطع ناگهانی دقیقاً بین ارسال موفق و ذخیره در دیتابیس، احتمال تحویل تکراری وجود دارد.

### بایگانی خودکار پس از انقضا

در جزئیات «اعلان انقضا» از مدیریت سرویس‌ها، مهلت بایگانی قابل تنظیم است؛ مقدار پیش‌فرض **۳ روز** و مقدار صفر به معنی توقف بایگانی خودکار است. تغییر مهلت نیاز به تأیید دارد، چون کاهش آن می‌تواند در بررسی بعدی حساب‌های قدیمیِ ازقبلمنقضی را بایگانی کند. توقف سرویس انقضا، بررسی بایگانی را هم متوقف می‌کند؛ «یک بار بررسی اکنون» بررسی و بایگانی واقعی انجام می‌دهد.

- دامنه فقط اکانت‌هایی است که سابقه معتبر ساخت توسط روت دارند. اشتراک شخصی خریدار ربات و مشتری ادمین در این بایگانی خودکار قرار نمی‌گیرد.
- برای انقضای زمانی، مهلت از timestamp پایان اعتبار محاسبه می‌شود. برای اتمام حجم، از اولین مشاهده پایان حجم توسط سرویس حساب می‌شود؛ پس از شارژ/مشاهده وضعیت فعال، شمارش آن دوره پاک می‌شود. شارژ اضطراری که اعتبار آینده ایجاد کند نیز مانع بایگانی حساب فعال می‌شود. عملیات اضطراری معلق اول باید بازیابی شود.
- هیچ سطری از پنل یا دیتابیس ربات حذف نمی‌شود. حساب در پنل بلاک می‌شود، از Driving List فعال کنار می‌رود و در Driving List مستقل بایگانی دیده می‌شود. مالکیت، پرداخت‌ها، دفتر کیف پول، روزهای اضطراری و لاگ فعالیت حفظ می‌شوند؛ رویداد بایگانی و snapshot فاقد رمز/توکن در تاریخچه مالک ثبت می‌شود.
- قبل از اعمال بلاک، پایان اعتبار و مقادیر مصرف/سقف حجم زیر قفل رکورد پنل دوباره بررسی می‌شوند. شارژ هم‌زمان باعث لغو بایگانیِ مبتنی بر وضعیت قدیمی می‌شود. سند معلق قبل از نوشتن در پنل ثبت می‌شود تا پس از restart همان عملیات بازیابی شود.
- جزئیات حساب بایگانی‌شده فقط خواندنی است. دکمه‌های قدیمی تمدید، آزادسازی، حذف و شارژ اضطراری اجازه تغییر آن را ندارند. تمدید خودکار هم حساب بایگانی‌شده را شارژ نمی‌کند.
- از بایگانی می‌توان با تأیید روت، حساب را به فهرست اصلی برگرداند. بازیابی به‌تنهایی زمان/حجم اضافه نمی‌کند و بلاک را برنمی‌دارد؛ پس از آن می‌توان تمدید یا آزادسازی کرد. اگر همچنان منقضی باشد، مهلت بایگانی تازه از زمان بازیابی در نظر گرفته می‌شود. سابقه بایگانی/بازیابی قبلی در تاریخچه باقی می‌ماند.

### شارژ اضطراری (Emergency Recharge)

این سرویس مستقل است و ابتدا غیرفعال می‌ماند. با حساب روت در تاپیک دلخواه بفرستید: `/set-topic emergency-trigger`، سپس از «مدیریت سرویس‌ها» آن را فعال کنید. نام ظاهری تاپیک می‌تواند Emergency recharge یا هر نام دیگری باشد.

- تنها اکانت‌های ثبت‌شده با سابقه ساخت توسط روت مشمول هستند؛ خرید شخصی، مشتری ادمین، اکانت بدون سازنده مشخص و حساب مسدودشده مالک مشمول نیستند.
- هنگام **انقضای زمانی**، یک روز از زمان فعلی اضافه می‌شود. اعتبار صفر/نامحدود یا صرفاً اتمام حجم باعث شارژ زمانی نمی‌شود. مصرف، سقف حجم و مسدودی در شارژ اضطراری دست‌نخورده می‌ماند.
- شمارنده روزهای پیش‌پرداخت در دیتابیس ربات باقی می‌ماند و در جزئیات اکانت و Driving List «شمارنده‌های اضطراری» دیده می‌شود. سقف پیش‌پرداخت هر دوره ۳۱ روز است؛ تا تسویه ماهانه، روز سی‌ودوم اضافه نمی‌شود.
- تمدید ماهانه از **همه دکمه‌های ماهانه روت**، شامل اعلان انقضا، اعلان اضطراری و جزئیات اکانت، برابر `max(0, 31 - emergency_days)` روز است. مثال: سه بار شارژ اضطراری → ۲۸ روز تمدید → شمارنده صفر. تمدید ماهانه، مانند قبل، مصرف را صفر و مسدودی را رفع می‌کند و برای اکانت روت هزینه‌ای از کیف پول کسر نمی‌کند. افزودن دستی «یک روز» یا تغییر زمان از عملیات سریع، تمدید ماهانه محسوب نمی‌شود و شمارنده را پاک نمی‌کند.
- اعلان اضطراری به تاپیک خودش می‌رود و دکمه تمدید ماهانه و لینک خصوصی وضعیت/اقدامات دارد. دکمه‌های دوره قبلی پس از تسویه، دوباره تمدید نمی‌کنند.
- عملیات قبل از نوشتن در پنل، به‌صورت سند معلق ذخیره می‌شود؛ پس از restart، همان هدف زمانی با مقایسه و قفل اکانت بازیابی می‌شود، نه یک روز اضافه دیگر. اگر پنل در میانه عملیات از بیرون تغییر کرده باشد، بازیابی با خطای تعارض متوقف می‌شود تا زمان یا شمارنده بی‌صدا بازنویسی نشود. روت باید عملیات معلق را بررسی کند.
- خطای ارسال تلگرام، شارژ را دوباره اعمال نمی‌کند؛ اعلان ثبت‌شده دوباره تلاش می‌شود. حذف اتصال تاپیک اضطراری، تا تنظیم مقصد معتبر، شارژهای جدید را متوقف می‌کند. توقف خود سرویس نیز از داشبورد ممکن است؛ در این حالت تمدید دستی همچنان پیش‌پرداخت قبلی را حساب می‌کند.

### دستورات گروه و تاپیک

`/help` راهنمای گروه را نشان می‌دهد. مدیر روت که مدیر گروه نیز هست می‌تواند:

```text
/set-topic recipt
/set-topic expired
/set-topic emergency-trigger
/unset-topic recipt
/unset-topic expired
/unset-topic emergency-trigger
/topics
/list-topics
```

نسخه‌های `/set_topic`، `/unset_topic` و `/list_topics` نیز پشتیبانی می‌شوند. حذف اتصال فقط از گروهی ممکن است که آن اتصال در آن ثبت شده؛ حذف یک سرویس به اتصال دو سرویس دیگر دست نمی‌زند.

### اعتبار منفی اختصاصی ادمین

در وضعیت ادمین یا جزئیات کاربر ادمین، «🏦 تنظیم حد منفی کیف پول» را انتخاب کنید و مثلاً `-5000000` بفرستید و تأیید کنید. این مقدار کف مجاز موجودی است، نه تغییر خود موجودی. مقدار پیش‌فرض صفر است؛ تنظیم هر ادمین مستقل بوده و برای کاربران عادی یا روت اعتبار منفی ایجاد نمی‌کند.

ساخت اکانت، شارژ مشتری و تمدید خودکار باید شرط `balance - price >= floor` را داشته باشند. بدهی و اعتبار قابل‌استفاده در وضعیت ادمین و کیف پول او دیده می‌شود. افزایش موجودی یا پرداخت تأییدشده، ابتدا بدهی را کم می‌کند و سپس به موجودی مثبت تبدیل می‌شود. کاهش سقف اعتبار بالاتر از بدهی موجود، یا تغییر سطح ادمین بدهکار به کاربر/روت، تا تسویه مجاز نیست.

برای تغییر دستی خود موجودی، `+50000` و `-50000` افزایش و کاهش هستند؛ `=-1000000` موجودی را دقیقاً منفی یک میلیون تنظیم می‌کند، فقط اگر کاربر ادمین بوده و کف مجازش اجازه دهد. تأیید نهایی دوباره کف مجاز فعلی را بررسی می‌کند. کاربران عادی همچنان نمی‌توانند موجودی منفی داشته باشند.

### کارت مدیریت اکانت V2

جزئیات اکانت برای روت شامل وضعیت، دانلود/آپلود و مصرف کل، حجم باقی‌مانده، انقضا و مدت دقیق باقی‌مانده، مجوز پنل، دعوت‌کننده، تاریخ ساخت، یادداشت، لینک قابل کپی و شمارنده اضطراری است. تاریخ‌ها در timezone تنظیم‌شده نمایش داده می‌شوند. فیلد `last_login_at` فقط «آخرین ورود به پنل» است؛ چون این جدول تله‌متری معتبر اتصال VPN ندارد، ربات آنلاین‌بودن یا آخرین اتصال را حدس نمی‌زند.

- «مشاهده کاربر ربات» فقط برای حساب شخصی دارای ارتباط ثبت‌شده در دیتابیس ربات نمایش داده می‌شود. برای اکانت ساخته‌شده توسط ادمین/روت، حتی اجرای callback قدیمی این دکمه رد می‌شود.
- تمدید ماهانه همان محاسبه کسر روزهای اضطراری را حفظ می‌کند. شارژ اضطراری دستی نیز فقط برای حساب روت واجد شرایط است. تمدید دلخواه تعداد روز مشخص را با تأیید اضافه می‌کند و شمارنده اضطراری را پاک نمی‌کند.
- «ثبت پرداخت» صرفاً دریافت پول را در دفتر مستقل پرداخت‌های دستی اکانت ثبت می‌کند؛ تأیید سفارش بانکی، شارژ کیف پول یا تمدید خودکار انجام نمی‌دهد. سوابق آن در Driving List جداگانه قابل مشاهده است و برای جلوگیری از شمارش دوباره، با گزارش درآمد سفارش‌های ربات ادغام نشده است.
- «تغییر بسته» انتخاب الگوی حجم و اتصال از بسته‌های ربات است. پیش از تأیید توضیح داده می‌شود که این عملیات فقط حجم مجاز و تعداد اتصال را تغییر می‌دهد؛ زمان انقضا، مصرف فعلی، شناسه پلن پنل، کیف پول و قیمت اختصاصی نماینده تغییر نمی‌کنند.
- حذف اکانت، ریست ترافیک و تعویض توکن/UUID دکمه تأیید دارند. جدول فعلی پنل فقط یک فیلد مسدودی `banned` دارد، بنابراین فعلاً یک کنترل بلاک/آزاد ارائه می‌شود، نه دو عملیات متفاوت با اثر نامشخص.

```text
/root
/set referral_reward 50000
/set support_username @my_support
/set payment_group_id -1001234567890
/set payment_topic_id 42
/price time-1c-1m 450000
/adminprice 123456789 time-1c-1m 350000
/discount time-1c-1m 20 48
/discountoff 1
```

`/adminprice` با Telegram ID نماینده، قیمت اختصاصی او را تعیین می‌کند. دستور `/discount` یک رویداد درصدی زمان‌دار می‌سازد؛ برای اعمال روی همه محصولات به‌جای کد محصول `all` بنویسید.

برای ویدئوی راهنما، `file_id` تلگرام را با کلیدهای `guide_android_file_id`، `guide_iphone_file_id`، `guide_windows_file_id`، `guide_mac_file_id` و `guide_linux_file_id` ذخیره کنید.

جست‌وجوی دیتابیس پنل سه حالت دارد:

- `id=32`: تطابق دقیق
- `email?ali`: شامل عبارت
- عبارت ساده: جست‌وجو بین email، token، uuid و remarks

## سرویس systemd

فایل نمونه در `deploy/vpn-shop-bot.service` قرار دارد. پس از بررسی مسیرها:

```bash
sudo cp deploy/vpn-shop-bot.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now vpn-shop-bot
sudo journalctl -u vpn-shop-bot -f
```

## نکات طراحی

ستون `users.v2accounts` برای سازگاری با طرح اولیه نگه داشته شده، اما منبع اصلی ارتباط، جدول نرمال‌شده `v2_account_links` است. این کار چند اشتراک برای هر کاربر، مالکیت نماینده و تمدید خودکار را بدون JSON شکننده ممکن می‌کند.

قیمت‌ها به «تومان واقعی» ذخیره می‌شوند؛ یعنی `450000` معادل ۴۵۰ هزار تومان است. قیمت‌های اتصال دوم فعلاً مقدار اولیه پیشنهادی‌اند و مدیر اصلی می‌تواند آن‌ها را تغییر دهد.

## مدیریت بسته‌ها و قیمت نمایندگان

### فهرست جدولی مشترک (Driving List)

تمام فهرست‌های داده‌ای مدیر اصلی و نمایندگان از یک جزء مشترک در
`vpnshopbot/driving.py` استفاده می‌کنند: کاربران V2، کاربران ربات، ادمین‌ها،
بسته‌ها، دسترسی و قیمت اختصاصی ادمین، مشتری‌های نماینده، انتخاب بسته، سفارش‌ها،
اشتراک‌ها، تنظیمات و دوستان دعوت‌شده.

- سرستون‌ها و سلول‌ها دکمه‌های جدا هستند؛ کلیک روی سلول، جزئیات ردیف را باز می‌کند.
- کلیک روی عنوان ستون، ترتیب صعودی/نزولی را تغییر می‌دهد.
- افزودن و حذف ستون (۱ تا ۵ ستون) برای هر شخص و هر فهرست مستقل ذخیره می‌شود.
- جست‌وجوی عمومی و فیلترهایی مثل `id=32`، `email?ali` و `name?ali` پشتیبانی می‌شوند.
- هر جست‌وجوی جدید داخل نتایج فعلی است؛ برگشت به جست‌وجوی قبلی و پاک‌کردن فیلترها وجود دارد.
- تعداد نتایج، صفحه فعلی، حرکت یک/سه صفحه، تازه‌سازی و حالت عملیات سریع نمایش داده می‌شوند.
- مالکیت مشتری و دسترسی ادمین در هر درخواست دوباره کنترل می‌شود؛ فیلترها جایگزین کنترل دسترسی نیستند.

### عملیات کاربران ربات

با انتخاب کاربر در فهرست جدولی کاربران، مدیر اصلی به عملیات زیر دسترسی دارد:

- غیرفعال‌سازی با دلیل اجباری و اعلام آن به کاربر، یا فعال‌سازی مجدد؛
- تنظیم موجودی، افزایش با `+مبلغ` یا کاهش با `-مبلغ` به تومان، با تأیید نهایی و ثبت تراکنش؛
- فهرست جدولی اکانت‌های V2 همان کاربر و ورود به جزئیات و عملیات کامل V2؛
- ارسال متن یا رسانه به روش کپی، یا فوروارد پیام، با لینک تماس مستقیم با پشتیبانی؛
- تاریخچه فعالیت در همان Driving List و مشاهده جزئیات هر رویداد و رسید مرتبط.

برای پیام کپی‌شده، دکمه پشتیبانی به خود پیام اضافه می‌شود. برای پیام فورواردشده،
Telegram اجازه تغییر دکمه‌های پیام را نمی‌دهد؛ دکمه در یک پاسخ متصل به همان پیام ارسال می‌شود.
شناسه پشتیبانی از تنظیم `support_username` خوانده می‌شود و می‌تواند `@username` یا شناسه عددی باشد.

حساب غیرفعال نمی‌تواند با دستور یا دکمه قدیمی به بخش‌های ربات دسترسی پیدا کند؛
دلیل اعلام‌شده و لینک پشتیبانی برایش نمایش داده می‌شود. حساب VPN و کیف پول حذف نمی‌شوند.
برای لغو عملیات در حال ورود پیام، `/cancel` یا دکمه انصراف را انتخاب کنید.

رویدادهای جدید در جدول مستقل `user_actions` ذخیره می‌شوند و شامل فرستنده، زمان،
نوع عملیات و مراجع سفارش/رسید هستند. سوابق مالی قدیمی از رکوردهای موجود بازسازی می‌شوند؛
کلیک‌های قبل از فعال‌شدن ثبت تاریخچه قابل بازیابی نیستند. کد احراز هویت در تاریخچه ذخیره نمی‌شود.
در جزئیات رویداد رسید، دکمه URL به پیام واقعی رسید در گروه می‌رود؛ نسخه فایل نیز قابل نمایش است.

### قیمت عمومی و اختصاصی

در داشبورد مدیر اصلی فقط «📦 مدیریت بسته‌ها» برای مدیریت قیمت فروش عمومی وجود دارد.
با انتخاب هر بسته، جزئیات، قیمت کاربران و وضعیت فروش عمومی دیده می‌شود و می‌توان
قیمت را با ارسال مبلغ به تومان تغییر داد.

در «🧑‍💼 مدیریت ادمین‌ها»، ادمین موردنظر را انتخاب کنید و به «بسته‌ها و قیمت اختصاصی» بروید.
بسته‌ها به‌صورت پیش‌فرض برای نماینده غیرفعال‌اند. با ثبت قیمت اختصاصی، همان بسته
فقط برای همان نماینده فعال می‌شود؛ می‌توان قیمت را تغییر داد یا دسترسی او به بسته را لغو کرد.
قیمت‌ها و تخفیف‌های عمومی روی قیمت توافق‌شده نمایندگان اثر ندارند.
قیمت‌های اختصاصی قبلی حفظ می‌شوند و به‌عنوان دسترسی فعال به همان بسته محسوب می‌شوند.

نماینده هنگام ساخت اکانت فقط بسته‌های مجاز خودش را می‌بیند. هزینه دقیق در پیش‌فاکتور
نمایش و پس از تأیید از کیف پول کسر و در دفتر تراکنش ثبت می‌شود.
از جزئیات اکانت مشتری می‌تواند مسدود/آزادسازی، تغییر توکن و UUID و شارژ با یکی از
بسته‌های مجاز خود را انجام دهد. شارژ روی همان اکانت انجام می‌شود، مصرف را صفر می‌کند
و هزینه همان نماینده را کسر می‌کند.

## برند شخصی نمایندگان

نماینده از داشبورد خود وارد «🎨 برند شخصی» می‌شود و می‌تواند نام برند را ثبت، تغییر، فعال یا غیرفعال کند. اکانت‌هایی که همان نماینده از داخل ربات می‌سازد، به برند او متصل می‌شوند.

سرویس `brand_api.py` با Gunicorn روی `127.0.0.1:24121` اجرا می‌شود و نام nodeهای subscription را بدون تغییر مشخصات اتصال بازنویسی می‌کند. برای فعال شدن لینک عمومی برند باید `BRAND_SUBSCRIPTION_BASE_URL` به یک مسیر HTTPS عمومی ختم‌شونده به `/` تنظیم شود و reverse proxy آن مسیر را به پورت محلی `BRAND_API_PORT` بفرستد. تا پیش از تنظیم این مسیر، ربات برای جلوگیری از تحویل لینک خراب از subscription اصلی استفاده می‌کند.
